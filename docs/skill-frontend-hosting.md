# Frontend Hosting — Skill Reference

**Important:** This repo (`stalker-m3u-server`) does not contain frontend source code. There is no `src/components`, no `.tsx` files, no Vite/React config — only the **compiled build output** lives here, in `public/`. The frontend source is maintained in a separate project/build pipeline and its output is copied into `public/assets/` as part of the release process.

Related: [[skill-database]], [[skill-auth-system]]

---

## What's Actually in This Repo

```
public/
  index.html              ← SPA entry point
  manifest.webmanifest     ← PWA manifest ("Stalker VOD", standalone display)
  sw.js, registerSW.js     ← PWA service worker (Vite PWA plugin output)
  workbox-*.js             ← Workbox runtime (offline caching)
  assets/
    index-{hash}.js        ← Main app bundle (hash changes every rebuild)
    index-{hash}.css
    vidstack-*.js           ← Vidstack player library chunks (video player)
    errors-*.js, prod-*.js  ← Vendor/error-tracking chunks
    srt-parser-*.js, ssa-parser-*.js  ← Subtitle parsing libraries
  *.png, *.ico, *.svg      ← PWA icons, favicons, logos
```

Every frontend rebuild produces new content-hashed filenames (e.g. `index-BCg-C-Fs.js` → `index-DglHRnDI.js`). Commit `dd178da` ("Frontend was pointing to static url") was a fix where the built bundle referenced a hardcoded/incorrect API base URL — fixed by patching the built JS directly (not by rebuilding from source, since source isn't in this repo).

### Samsung Tizen TV target
`public/index.html` loads `<script src="$WEBAPIS/webapis/webapis.js">` — the Tizen Smart TV WebAPIs shim. This confirms the SPA is built to also run as a Samsung Tizen TV app (`$WEBAPIS` is a Tizen-injected path, harmless no-op outside that runtime). Relevant if debugging TV-specific playback or input issues — the device-code flow in [[skill-auth-system]] exists precisely because TV apps can't do browser OAuth redirects.

## How the Server Serves It (`src/server.ts`)

### Root route
`GET /` → always serves `public/index.html` with a permissive CSP header (`default-src * 'unsafe-inline' 'unsafe-eval' data: blob:;`) needed for the SPA's inline scripts and dynamic media URLs.

### Catch-all route (SPA fallback)
`GET /{param*}` — registered **after** all API routes:
- If the requested path has a static asset extension (`.js`, `.css`, `.png`, `.jpg`, `.svg`, `.webmanifest`, etc.) or starts with `uploads/` → serve the file directly from `public/`
- Otherwise → serve `public/index.html` (client-side router handles the path)

This is standard SPA hosting: deep links like `/contentmanager` or `/#/verify?code=...` resolve to `index.html`, and the frontend router takes over.

### Static file serving
Uses `@hapi/inert` (`Inert` plugin) registered once in `init()`.

## Auth Interceptor and Frontend Routes

A global `onPreHandler` hook in `server.ts` enforces JWT auth on `/api/*` and `/v2/*` paths, with exceptions for:
- Static pages (anything not under `/api/` or `/v2/`)
- `/api/auth/*` (login/signup must be reachable unauthenticated)
- `/api/images/*`, `/api/proxy*`, `/api/media/*`, `/api/vod/*` (stream/image proxies — tokenless by design)
- `/live.m3u8`, `/player/*`, `/live/*`, `/movie/*`, `/series/*`, `/portal/proxy` (legacy/player-facing stream URLs, secured by HMAC signing instead of JWT — see [[skill-m3u-playlist]])

The frontend SPA itself (served via the catch-all) is never gated — only its API calls are.

## PWA / Offline Support

- `manifest.webmanifest` declares the app as installable: standalone display, dark theme (`#111827`), maskable icons
- `sw.js` + `workbox-*.js` — generated by a Vite PWA plugin (vite-plugin-pwa) in the frontend build; provides offline asset caching
- `registerSW.js` — boilerplate service worker registration snippet

The frontend is a SPA client consuming this server's REST + WebSocket APIs. Relevant API surfaces it depends on (each documented in its own skill file):

|---------------|-------------------|

## Implication for Future Work

Because frontend source isn't versioned here, **any frontend logic bug can only be fixed by**:
1. Patching the built JS in `public/assets/` directly (fragile, only done for urgent fixes — see `dd178da`), or
2. Rebuilding from the separate frontend repo and copying the new `public/` output into this repo

If asked to "fix the UI" or change frontend behavior, check whether the actual frontend source repo is available before attempting to hand-edit minified bundles in `public/assets/`.
